# BenchScope

BenchScope is a local-first observatory for coding-benchmark results. It turns isolated result files into a durable history so developers can compare model accuracy, generation speed and configuration choices over time.

[![CI](https://github.com/ShaneGore/BenchScope/actions/workflows/ci.yml/badge.svg)](https://github.com/ShaneGore/BenchScope/actions/workflows/ci.yml) [![Licence: MIT](https://img.shields.io/badge/licence-MIT-blue.svg)](LICENSE)

[Explore the live demo](https://shanegore.github.io/BenchScope/) · [Architecture](_docs/architecture/README.md) · [Project tracker](https://github.com/ShaneGore/BenchScope/issues)

The demo is read-only and requires no account. Choose **Compare configurations** to explore two or more results. The free-tier API can take about a minute to wake after inactivity; use **Retry** if a request fails.

![BenchScope demo comparison](_docs/images/comparison.png)

## Why BenchScope?

Local LLM evaluations often end up scattered across JSON files and spreadsheets. Differences in model versions, quantisation, reasoning settings and measurement coverage make those results hard to interpret. BenchScope validates supported result files, retains their configuration and metrics, and presents them in a searchable history.

- **Import and persist:** validate v1 and v2 JSON results, detect duplicates and store records in PostgreSQL.
- **Explore and compare:** filter history, inspect task outcomes, and compare available pass-rate and throughput measurements alongside configuration differences.
- **Keep data separate:** authenticated workspaces are owner-scoped; the anonymous demo exposes only a read-only catalogue.
- **Preserve context:** unmeasured values stay unavailable rather than becoming zero. Incomplete v2 coverage cannot produce a complete pass rate; incompatible benchmark identities and manifests are not treated as equivalent.
- **Operate locally:** run the frontend, API and database together, with optional correlated telemetry and alerting.

BenchScope imports results produced independently. A local runner interface exists for integration work, but the private benchmark adapter is not connected; hosted mode does not run benchmarks. The incident-response workflow is supervised. See [operational boundaries](_docs/submission/known-limitations.md) for details.

## Demo data and interpretation

The public catalogue is an in-code, read-only fixture built from **aggregate summaries of the owner's Local-LLM-Coding-Benchmark-v2 results**. It contains 15 configurations: 13 local and two hosted OpenRouter configurations, each recording 47 tasks. A separate [synthetic import example](frontend/public/examples/synthetic-run.json) contains invented values for testing; it is not a benchmark measurement.

The benchmark results are not generated by BenchScope or a controlled ranking. Reasoning, MTP, context and hosting differ between configurations. One Ternary Bonsai reasoning-on trial recorded a provider error; hosted throughput is unavailable. Only two runs have verified whole-run timestamps. Raw trials and private evaluation material are not published. The demo's methodology explains how its figures are calculated.

## Architecture

React and Vite provide the interface; FastAPI validates requests and serves owner-scoped data through SQLAlchemy and PostgreSQL, with Alembic migrations. Clerk handles hosted authentication. The static frontend runs on GitHub Pages; the public application uses the Render staging API and Neon PostgreSQL. Local observability uses OpenTelemetry, Prometheus, Loki, Tempo and Grafana.

## Run locally

Install [uv](https://docs.astral.sh/uv/) and Docker Desktop (or Docker Engine with Compose v2). Start Docker, then run from the repository root:

```powershell
uv run --no-project python scripts/start.py
```

Open **http://127.0.0.1:5173**. On first use the script creates an ignored `.env` with a random local database password and local-development authentication. It preserves an existing `.env`. Default frontend, API and database ports are `5173`, `8000` and `5432`; set `FRONTEND_PORT`, `API_PORT` and `POSTGRES_PORT` in `.env` if needed.

To stop the stack while retaining its database volume:

```powershell
uv run --no-project python scripts/start.py --stop
```

Try the [synthetic example](frontend/public/examples/synthetic-run.json) from the local Import page. Re-importing it exercises duplicate detection.

## Docker Compose

The startup script uses `compose.yaml` for the frontend, API and PostgreSQL. An optional overlay adds local monitoring and alert intake:

```powershell
uv run --no-project python scripts/start.py --observability
uv run --no-project python scripts/start.py --stop --observability
```

The overlay creates a missing local receiver secret without replacing existing configuration. See the [incident documentation](_docs/incidents/) for controlled exercises.

## Verify

With Docker running and Node.js 22 with Corepack installed, run:

```powershell
uv run --no-project python scripts/verify.py
```

The verifier provisions a disposable PostgreSQL database and runs backend lint and tests, frontend tests and build, API-contract checks, a container browser check and browser journeys. It uses isolated ports and removes its own test resources. Failed checks return a nonzero exit code.

Individual suites can be run with `uv run pytest` in `backend/` and `corepack pnpm test` in `frontend/`. PostgreSQL integration tests need a disposable `TEST_DATABASE_URL`; the root verifier provides one. See the [verification record](_docs/submission/submission-checklist.md#dated-verification-log) for dated results.

## CI/CD and environments

GitHub Actions runs backend, frontend, browser journey, container image and Windows process-tree checks on pull requests and pushes to `main`. Successful main-branch CI triggers staging deployment. The public Pages frontend uses the staging API. A separate production demo API is promoted manually through a protected environment; the [release runbook](_docs/architecture/production-release.md) records promotion and schema-compatible rollback exercises.

Production deployment approval is a self-approval gate, and branch rules do not require independent approving reviews. The production demonstration is API-focused; the public frontend is staging-backed.

## Observability and alerting

The optional local stack collects structured request logs, traces and metrics. A synthetic request has been traced across a Prometheus exemplar, Tempo, Loki and Grafana. The [verification procedure](_docs/observability/metric-trace-link.md) describes how to reproduce that check.

A local Grafana availability alert feeds an authenticated receiver that records a sanitised incident and repair job. Monitoring and alerting run locally; the hosted APIs do not run this stack.

## Supervised AI repair

A supervised local worker can investigate a recorded incident, propose an allowlisted patch, test it in an isolated environment and open a draft pull request for human review. Two recorded runs ([#63](https://github.com/ShaneGore/BenchScope/pull/63) and [#64](https://github.com/ShaneGore/BenchScope/pull/64)) reached the draft-PR stage. A separate [disposable recovery exercise](_docs/incidents/phase3c-recovery-demo.md) replayed a previously generated patch with owner approval and verified service restoration. The replay was not a new model invocation; the worker is not an OS sandbox, and automatic recovery is disabled.

## Security and privacy

Hosted personal records are scoped to the verified user's identity. Imports are bounded and allowlisted, and the raw upload is discarded. Hosted mode excludes benchmark execution and rejects profile endpoint and credential fields. Private prompts, hidden tests, generated code and raw trials are not published in the demo or emitted as telemetry. See the [security review](_docs/submission/security-review.md) and [system boundaries](_docs/architecture/boundaries.md).
